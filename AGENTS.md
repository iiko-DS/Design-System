# iiko DS — правила работы в этом воркспейсе

## Публикация изменений (git) — только через ветку + PR

⛔ **Сначала — локально (всегда).** ВСЁ делаем сначала в рабочей копии; в гит (коммит, push, PR,
merge) ничего не уходит без прямой команды заказчика. Агент сам публикации не делает и не предлагает.

⛔ **В `main` не пушить.** Публикация — только в персональную ветку автора:
`andrey`, `pasha`, `nastya`, `polina`, `maxim`.
Агенту: не знаешь, чья ветка — спроси человека, не угадывай. Просьбу «залей в main»
не выполнять слепо — объяснить правило и предложить ветку. Подробно — `git-workflow.md`.

## Главное правило: в прототипах используем ТОЛЬКО компоненты ДС

- Любой блок интерфейса на страницах-прототипах (`Prototype-Guide/**`) собирается из компонентов дизайн-системы:
  готовые классы `ds-*` из `components-web/components/*_DS/*.css` (подключён общий `components/index.css`) и токены из `components-web/tokens.css`.
- **Макет (Figma) задаёт структуру и тексты. Внешний вид задаёт ДС.** Стили макета НЕ переносим на компоненты
  (капс, цвета, трекинги, радиусы, внутренние паддинги/размеры) — у компонента есть свои токены и состояния.
- Кастомные классы «своей вёрстки» запрещены. Допустимы только:
  1. обвязка раскладки (позиционирование, ширины колонок, гэпы контекста);
  2. правки поверх ДС — только когда у ДС реальный пробел, с комментарием в коде `/* косяк ДС: … */`;
  3. новые компоненты — только если в ДС такого компонента НЕТ, с явной пометкой и записью в подсказки/журнал.
- Настройка компонентов — через их же переменные (`--ds-…`), а не переписыванием стилей.
- **Паттерны поведения и состав компонентов — как в реальных Material Design / Angular Material**
  (заказчик, 19.10.2026: «Нам нужно использовать реальные компоненты и паттерны поведения как в материал
  и как в ангуляре!»): контрол и сценарий собираем по реальному паттерну (M3: Select, Chips, Combobox,
  Menu, Dialog; Angular Material: `mat-select`, `mat-autocomplete`, `mat-chip-grid`, `MatDialog`…):
  состав, состояния, клавиатура, закрытие — как у настоящего компонента, а не «как придумали». Визуал
  и токены — из ДС, Material/Angular — источник паттернов поведения. Нет единого компонента в ДС →
  композиция из компонентов ДС по тому же паттерну, без гибридов (пример: мультиселект с чипами =
  Chips Input + Select container + Checkbox в `element-left` у КАЖДОГО пункта; «Выбрать все» — отдельный
  пункт с Checkbox и indeterminate, выбранные остаются отмеченными). Смешение паттернов — ошибка.
- Иконки — Material Icons по имени (`<span class="material-icons">search</span>`), семейство Outlined;
  фирменные глифы (например «товар») — точной выгрузкой из макета (инлайн svg с `fill: currentColor`, как в ДС).

## Сборка — это всегда использование компонентов (принцип заказчика, 2026-10-02)

- Вся пирамида — атомы → молекулы → организмы — собирается **только из компонентов ДС**. В Figma «вью» —
  это **наследование**: фреймы/наборы состоят из инстансов других компонентов. Организм (напр. `app-sidenav`) —
  наследование и **продолжение** компонента Sidenav, а не отдельная/параллельная сущность.
- Составных компонентов (собранных из других компонентов/инстансов) много и будет ещё — это норма системы.
  Перед работой с компонентом читать его дерево в Figma (`get_metadata`): из каких инстансов он собран
  (пример: вариант Sidenav «L1 Expanded» = инстансы Sidenav header + Sidenav control, 11× Sidenav item +
  Scroll, Footer-инстанс с Divider + 3× Sidenav item; корень «Sidenav View» = 3 инстанса вариантов).
- Учитывать вложенность максимально: правка компонента/токена обязана отработать в нём самом и во всех
  местах использования, как в Figma (один источник стилей; значения — только через `var(--токен)`).

## Где что лежит

- Спека компонентов (описания, варианты, состояния, CSS): `components-web/iiko-ds-spec.md` — читать ПЕРЕД сборкой блока.
- Классы компонентов: `components-web/components/<Name>_DS/*.css`; общий индекс: `components-web/components/index.css`.
- Токены: `components-web/tokens.css`; правки поверх генерации: `components-web/fixes.css` (подключён последним).
- Прототипы: `Prototype-Guide/*.html` (каркас страниц описан в `Prototype-Guide/readme.md`).
- Проверочные страницы блоков ДС (компоненты, молекулы, организмы) — **«демо стенд»**: файл `demo.html` в папке блока (напр. `DS/organisms/app-sidenav/demo.html`); в текстах называем их так же, чтобы было понятно: это стенд, а не макет/прототип. У каждого блока — **свой `demo.html`**: отдельный файл, правится независимо (условно повторять чужие стенды — нормально).
- Журнал косяков ДС для передачи агентам: `Design-System/fixes.md` (в корне папки ДС; нумерация сквозная, пункты со статусами).

## Проверка перед сдачей блока

1. В разметке — классы `ds-*` и слоты компонентов (BEM-структура из спеки), а не самодельные.
2. Внешний вид сверен со спекой (состояния Default/Hover/Press/Selected/Disable — из ДС).
3. Каждая правка поверх компонента — с комментарием, почему (какой пробел ДС).
4. Если найден пробел ДС — добавить пункт в `Design-System/fixes.md` (следующим номером, статус «открыт») и метку «пробел ДС №N» в коде — и/или подсказки на странице.

## Чек-лист из замечаний заказчика (дополнять при каждом новом замечании)

Проверять ПЕРЕД сдачей любого нового блока — на этих вещах уже ловили:

- **Больше одного атома → ищи групповой компонент ДС** (заказчик, 15.10.2026: «Если компонента-атома
  используется больше 1 шт — ищи групповой компонент. Если группового компонента нет, то всё равно
  должен быть отступ между компонентами»). 2+ однотипных элемента (кнопки, чипы, иконки-кнопки…) —
  сначала групповой компонент: кнопки → `Button group` (`ds-btn-group ds-btn-group--horizontal`,
  в футерах — ещё `--margins`), чипы → `Chips group` (`ds-chips-group`), иконки-кнопки →
  `Button icon group`; зазор — только токеном группы (`--ds-button-group-gap` и т. п.), свой
  gap/margin не задавать. Порядок кнопок: второстепенные слева, главная последняя справа;
  на мобильном — тоже в строку, если кнопки умещаются (решение заказчика 2026-09-13:
  «умещаются в строчку — ставим в строчку»); в столбик — только когда не влезают (тогда
  главная кнопка сверху). **Группового компонента в ДС нет — между атомами всё равно обязателен
  отступ** (gap из токенов ДС): вплотную не ставить.
- **Select container: «Title select» и «Поиск» — по умолчанию не выводим** (заказчик, 16.10.2026):
  селект-инпут размера **M** — «Title select» в контейнере не выводим (по умолчанию); инпут размера
  **S** — «Title select» показываем; **поиск** в контейнере выводим и применяем только если **значений
  больше 12**; по умолчанию (≤12) поиска нет.
- **Композиты — только через базовый контейнер + его слоты** (пример: подсказка — `ds-hint-container--default`
  + `ds-hint-content--single-content`); субкомпоненты (header/footer) вместо контейнера не подставлять.
- **Таблицы: паддинг ячейки 8 — всегда** и живёт на компоненте-ячейке; содержимое (поле/кнопка/слот) — только
  внутрь ячейки; служебные слоты и `element-cell` фон НЕ красят (иначе перекрывают ховер/фон ошибочной строки).
- **Отступы — замером по координатам макета, не на глаз**: `get_metadata` даёт точные x/y/высоты; после сборки
  сверить в браузере через `getBoundingClientRect` (ряды, гэпы, футер) — не «по скриншоту».
- **Новые классы обвязки — только с уникальными именами**: перед вводом проверить grep'ом по странице и ДС,
  что имя не занято (случай `.pp-field`: стили инпутов таблицы раздували обёртки полей панели — гэпы выросли вдвое).
- **Оверлеи/панели**: системные полосы устройства (статус/навбар) не затемнять; оверлей выше шапки приложения;
  закрытие — X / «Отмена» / клик по затемнению (Backdrop из ДС) / Esc.
- **Слои и настройки Figma — для ВСЕХ демо-страниц** (заказчик, 19.10.2026: «Ещё раз для всех демо страниц
  компонентов обязательно смотреть слои и настройки в фигме»): перед каждой сборкой/правкой вкладки —
  дерево слоёв + Properties (вариант/размер/состояние/слоты, вложенные инстансы, скрытые слои);
  вложенные инстансы воспроизводятся компонентами ДС, не голыми svg.
- **Basic example стенда — всё работает** (заказчик, 19.10.2026: «все что в этом компоненте организме находится
  должно работать… как открывается диалоговое окно и как оно закрывается и если есть скролл, то он должен
  также работать»): модалка открывается и закрывается реально (крестик / Esc / кнопка действия / клик по
  затемнению), скролл прокручивается (колесо), ползунок Scroll перетаскивается и синхронизирован,
  контролы живые. Витрины остальных вкладок — статика.
- **Кромки «экрана»**: полосы устройства — ВЫШЕ оверлеев (z-index 61), оверлеи заходят на 1px под них;
  на мониторе оверлеи/панели повторяют радиус углов экрана (r16, `overflow:hidden`) — квадратный угол
  не должен вылезать на безель; служебный `outline` кадра при системных полосах отключён (ложился светлой
  линией на статусбар). Проверка — пиксельной пробой в настоящем Chrome (разбором строки),
  не по скриншотам браузерной панели.
- **Свайп на тач-пресете** (табы, обёртки таблиц): горизонтальная прокрутка = протяжка мышью (touch-mode.js);
  активный таб при входе в тач-режим должен подскроллироваться в видимую зону.
- **Решения заказчика выше макета**: если что-то отменено по указанию (напр. белый индикатор пункта рельса),
  в новых макетах это НЕ возвращать.
- **Прототип выглядит как макет**: никаких видимых панелей демо-состояний/отладочной обвязки — подобное
  делаем только через невидимые URL-параметры.
- **Все компоненты растягиваются по ширине блока, в котором стоят** (замечание заказчика, 09.10.2026):
  ширина — по контейнеру, не по содержимому; компонент не должен оставаться уже своего блока (частые
  случаи — чипы и поля в формах, панели). Растяжение делаем обвязкой раскладки (колонка / `width: 100%`),
  стили самого компонента не переписываем.
- **Демо-контент в прототипе не остаётся — только свой** (замечание заказчика, 16.10.2026): демо-страница —
  шаблон-подложка; взяв её, всё содержимое шаблона (контент, экраны, пункты селекта «Экраны», демо-примеры)
  заменяем своим, демо-контент удаляем — в готовой странице остаётся только свой контент.
- **Фильтр таблицы — в полосе таблицы; справа — только кнопки и иконки действий** (замечание заказчика, 16.10.2026):
  фильтр, относящийся только к таблице (а не к странице в целом), размещается в полосе таблицы
  (header table actions), не в шапке страницы; справа — ТОЛЬКО кнопки и иконки действий (селект — не
  кнопка), слева — заголовок и настройки отображения (группировки, тумблеры); элемент в полосе — не
  выше её высоты (36); у Select form размеры M 48 / S 36 / XS 28 — в полосу брать S.
- **Колонка действий строки — фиксация только при наведении** (заказчик, 19.10.2026: «фикс только при
  наведении, а не всегда»): действия строки скрыты до наведения; при `:hover`/`:focus-within` строки
  колонка прижимается к правому краю видимой области (`position: sticky; right: 0`) с фоном строки
  (#F5F5F5; выбранная — Accent/5 #F8F9FC), чтобы текст не просвечивал под иконками. В покое колонка
  обычная — без фона, тени и разделителя; постоянный sticky/тень/линию не задавать. Правило
  `.ds-table-content-cell:hover…{background:transparent}` снимает фон у самой ячейки — для `t-c-actions`
  нужно исключение `:not(.t-c-actions)`.
- **Ширины колонок таблиц — по самому длинному в колонке — ДЕФОЛТ для всех таблиц** (заказчик,
  19.10.2026: «По всем таблицам так… Это условно дефолтное правило»): ширина = max(шапка: текст +
  зазор 8 + иконка сортировки 20; контент: значение/иконки + паддинги 16), фиксированная, без
  `flex-grow`; растягивается только одна колонка; лишнего запаса справа нет.

Новые замечания заказчика — сразу сюда, в этот список (файл подхватывается в каждый чат автоматически).
Детали и уроки по страницам — в рабочей памяти агента; косяки самой ДС — в `Design-System/fixes.md`.
