# Table -> Jira: эпик и задачи по макету iiko Web DS

Документ для переноса в Jira. Подготовлен 2026-10-21 по сверке макетов Figma (Iiko-Web-DS-New) с реализацией `@iiko/table` (RestoTable 22.0.2) на `frontend-common.iiko.ru`.

Редакция 2 (2026-10-21): сняты пересечения между задачами (З1 / З5 / З10), разделены перегруженные задачи (З6, З12), убрано противоречие метки у З15 и З16, добавлены связи с уже заведёнными задачами, типы и приоритеты переведены в значения iiko Jira.

## Как использовать этот файл

- Создать **один эпик** с описанием из раздела 1.
- Создать **15 задач** из раздела 2 (по макету: З1 - З13, плюс З6б и З12б) и привязать их к эпику.
- Создать **5 задач** из раздела 3 (паритет с table-grid: З14 - З18) - тоже в эпик.
- Создать **1 отдельный тикет** из раздела 4 (вне эпика).
- Поля каждой задачи: Тип, Приоритет, Метки, Макет (прямые ссылки на блоки), Что сделать (с компонентами), Уже есть, Открытые вопросы, Приёмка. Порядок работ - один на весь эпик, в разделе «Порядок выполнения»; в задачах стоят только реальные зависимости.
- Компоненты ДС - названиями из Figma (по узлу самой задачи), чтобы разработчик собирал из того же, что нарисовано. Внутренние компоненты таблицы (`Table header cell`, `Table content row`, `Table content cell`, `Element cell`, `Element left/right`, `Text UI`, `State`, `Icon size`) - это части самого компонента Table, их с нуля не рисуем. Где в Figma есть отдельный компонент (`Checkbox`, `Button`, `Badge`, `Status`, `Chips`, `Divider`, `Menu item`, `Search`, `Input number`, `Select list`) - берём его, а не свою вёрстку.
- Если элемент в макете - собранный компонент, в задаче пишется только он (`Menu (Container)` для панелей и меню, `Chips input cell`, `Table 2 lvl` и т.п.), а внутренности (пункты меню, чекбоксы, кнопки, разделители) не перечисляются: они уже внутри. Перечислять внутренности нужно, только если чего-то требуемого в компоненте нет.
- Каждый пример в доке собирается из компонентов ДС, перечисленных в задаче; своих элементов в примерах быть не должно. Если нужного компонента в ДС нет - стоп и вопрос, а не своя вёрстка.
- Список компонентов в задачах сверен с сайтом компонентов. Сверка с Figma-файлом не сделана (в этом контуре Figma недоступна) - при заведении задач этот шаг нужно пройти.
- В приёмку каждой задачи входит пример в `table/examples` и запись в changelog пакета - отдельным пунктом в задачах не повторяется.
- Где смотреть, что уже работает: живые примеры компонента (13) и примеры старого `table-grid` (11), ссылки - в разделе 1 «Где смотреть реализацию».
- Ничего не додумывать: если в задаче написано «уже есть» - это проверено по коду/докам, дублирующую задачу создавать не нужно.
- Открытые вопросы из задач не удалять: это границы, где решение принимает дизайн или команда.

Ссылки в задачах ведут на конкретный блок макета, а не на большой раздел, чтобы блок не искать внутри страницы.

## Как расставлены приоритеты

Приоритеты - оценка на основе макета, а не замер использования в приложениях: данных о том, где какие механики нужны, на момент постановки нет. Разработчики могут переставить по своим данным (см. «Что поменяет приоритет»).

Шкала: `P1 = 1 - Must have`, `P2 = 2 - Should have`, `P3 = 3 - Nice to have`.

Критерии (по убыванию веса):

1. блокирует ли задача другие задачи эпика;
2. насколько широко видно расхождение: каждый экран с таблицей или один сценарий;
3. базовая механика по макету или точечный сценарий;
4. есть ли нерешённый вопрос (если задача упирается в вопрос без ответа - срочность ниже).

**P1 (6 задач)** - видно везде, базовая механика макета или блокирует другие задачи:

- З1 токены - видно на каждом экране;
- З2 фильтр в заголовке - базовая механика макета, часть состояния таблицы;
- З5 состояния строки - видно везде, «активная строка при открытом сайдбаре» ломает основной сценарий;
- З6 состояния ячейки и error - ошибка ввода видна пользователю;
- З9 панель столбцов - обязательное правило макета, механика состояния уже есть;
- З14 реактивная смена колонок - блокирует З9 и З11.

**P2 (10 задач)** - отдельные сценарии, или упираются в нерешённый вопрос, или основное уже работает:

- З3 разделители (нужны не всем таблицам, открытый вопрос по вариантам);
- З4 двухуровневый хедер (нужен части отчётов, обходной путь через свой `thead` есть);
- З6б chips-ячейка (новый тип ячейки, опирается на компонент Chips ДС);
- З7 hover-действия (конкретные экраны, открытый вопрос про иконки);
- З8 перетаскивание строк (механика работает, не хватает визуала);
- З11 добавление строк и колонок (новый функционал, открытый вопрос: компонент или приложение);
- З12 футер таблицы (фиксация есть, нет быстрых фильтров);
- З13 раскрытие деталей (точечный сценарий, для дерева есть);
- З15 группировка (паритет, нужна немногим, вопрос архитектуры);
- З16 auto-высота (нужна при двухстрочном контенте).

**P3 (4 задачи)** - косметика низкой частоты или паритет без подтверждённого спроса:

- З10 зебра и бордер;
- З12б футер страницы (отдельный компонент, не часть таблицы);
- З17 поиск по таблице (вне раздела механик макета);
- З18 конфиг сохранения состояния (нужен для отдельных случаев приёмки З9).

**Что поменяет приоритет:**

- появился список приложений и экранов с таблицей: если фильтры собраны снаружи - З2 вниз до P2; если панель столбцов уже есть в приложениях - З9 вниз до P2;

- на table-grid осталось много приложений - З15, З16, З17, З18 вверх до P1/P2.
